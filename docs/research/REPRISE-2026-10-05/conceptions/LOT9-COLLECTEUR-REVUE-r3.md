# Revue indépendante — collecteur stage r1

Lecture seule, sans QA. Revue bornée au chemin `attempt-prompt-submit → admission → runtime.callTool → observe → SQLite enqueue`. Les références sont les fichiers copiés dans `/dev/shm/opsys-lot9-collecteur-raccord-stage-r1/files`; stage non gelé.

## Constats vérifiables

1. **Backpressure absent si l’enqueue local échoue.** `OpsysPostflightCollector.#enqueue` absorbe deux échecs et garde le fait dans `#pending` (`core/src/agents/harness/opsys-postflight-collector.ts:219-240`). `flushPending` retente seulement plus tard (`:208-217`). Le prochain `assertBeforeEffect` (`:128-141`) ne vérifie pas `#pending`, donc d’autres effets peuvent survenir pendant que l’observation antérieure n’existe qu’en mémoire. Le quota par tentative de 20 est bien réservé synchroniquement avant effet (`:136-141`); la limite durable 256 lots/1 MiB de l’outbox n’est pas réservée par ce collecteur. **Test à ajouter :** faire échouer toutes les écritures d’un premier résultat connu; le call suivant doit rester avant effet tant que l’observation précédente est non durable, puis être autorisé après drainage confirmé. Aucun outil/provider supplémentaire durant la panne.

2. **Un reçu d’admission invalide ne révoque pas l’ancien reçu conservé.** `recordRuntimeAdmission` retourne silencieusement sur validation négative (`.../opsys-postflight-collector.ts:67-82`) sans effacer `#runtimeAdmission`; `beginToolCall` utilise ensuite le reçu présent (`:111-124`). Le callback normal `onAdmitted` est produit après validation par `createOpsysRuntimeAdmissionStreamFn` (`core/src/agents/embedded-agent-runner/opsys-runtime-admission.ts:432-442`), donc l’entrée invalide n’est pas démontrée sur le chemin courant; la méthode publique laisse néanmoins un état stale en cas de nouveau producteur/transition. **Test discriminant :** reçu valide, puis candidat/reçu invalide ou profil-révision incohérent; aucun call ne doit réutiliser le précédent reçu.

3. **Un rejet de validation post-call saute l’observation.** Le runtime reçoit le résultat distant, puis exécute `validateResult` avant `postflight.observe` (`core/src/agents/agent-bundle-mcp-runtime.ts:1204-1229`). Une mutation peut donc avoir répondu, mais une erreur de validateur ressort sans observation. Le post-check d’abort, lui, est correctement placé après `observe` dans `runMcpRequest`; le test couvre un résultat structuré malgré abort côté client (`.../agent-bundle-mcp-runtime.opsys-cible-ticket.test.ts:206-238`). **Test discriminant :** réponse métier structurée connue + `validateResult` qui lève; vérifier une observation de l’issue connue si décodable, sans replay d’effet, et distinguer ce cas d’un rejet transport sans résultat.

4. **La déduplication historique ne distingue pas les tentatives.** La clé fact reste `depositKey(sessionId, toolCallId)`, tronquée à 40 hex (`core/src/context-engine/opsys-contexte-depot.ts:79-83`). `#usedCallIds`/`#knownFacts` vivent sur un collecteur d’une tentative (`.../opsys-postflight-collector.ts:31-47,119-120,195-203`); le reçu runtime porte pourtant run/attempt/cycle (`core/src/agents/embedded-agent-runner/opsys-runtime-admission.ts:432-442`). Si un fournisseur réutilise le même `toolCallId` pour une autre tentative du même `sessionId` et que le contenu/cible diffère, l’outbox rejettera la clé en contenu divergent; les essais locaux gardent alors l’enveloppe seulement en mémoire. **Test discriminant :** même ID sur deux admissions/fallbacks d’une session, même puis contenu divergent; le premier fait reste exact, aucun écrasement ni second effet dû au replay; collision divergente apparaît comme échec conservé/revue. Ne pas changer la clé historique.

5. **Le stage ne prouve pas encore le seam avec SQLite réelle.** `opsys-postflight-collector.test.ts:4-14` mocke l’ouverture DB et l’enqueue; le test du runtime MCP observe un spy de callback (`.../agent-bundle-mcp-runtime.opsys-cible-ticket.test.ts:122-163,186-238`). Aucun test fourni ne relie le vrai `attempt-prompt-submit`, le runtime ticketé, le collecteur et une base temporaire/outbox persistée. **Test discriminant :** parcours réel unique pour un MCP structuré, puis réouverture SQLite et vérification de lot, clé, département/profil/révision, cible affaire, replay idempotent et absence de second effet après abort post-retour.

Le chemin du reçu DB est correctement canonique dans le stage: après attente de persistance et concordance agent/session/clé, `storePath` est transmis comme `options.path` (`.../opsys-postflight-collector.ts:84-109`); le test l’assert (`.../opsys-postflight-collector.test.ts:81-89`). Le reçu ticket sépare affaire/serveur/outil et vérifie sa concordance avant capture (`.../opsys-contexte-cible-ticket.ts:167-176`; collecteur `:158-166`).
