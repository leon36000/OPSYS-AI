## 1. Défauts connus — preuves de code et correctifs

### 1.1 Jointure ROI `google` vs `google_ads` (silencieusement cassée sur données réelles)

Preuve croisée de trois fichiers :
- `Modules M/M7-marketing/fixtures/matomo/visites.v1.yaml` — `utm_source: google` (le canal réel).
- `Modules M/M7-marketing/src/attribution/attribution_engine.py:119-126` — `par_canal` est indexé
  par `utm_source` BRUT (donc la clé `"google"`, jamais transformée).
- `Modules M/M7-marketing/src/ads/ads_loader.py:17` — `ALLOWED_PLATFORMS = {"google_ads", "meta"}` ;
  `fixtures/ads/google_ads.yaml:2` → `plateforme: google_ads`.
- `Modules M/M7-marketing/src/roi/roi_engine.py:62` —
  `campagnes_plateforme = campagnes_par_plateforme.get(canal, [])` : cherche la clé `"google"`
  dans un dict indexé par `"google_ads"`/`"meta"`. **Aucune correspondance possible** → pour le
  canal réel `google`, `campagnes_plateforme` est toujours vide → `donnees_insuffisantes:
  cout_indisponible`, jamais de `cout_par_lead`, même quand un coût Google Ads existe réellement
  pour la même fenêtre.
- La suite `tests/roi/test_roi.py` (classes `TestJointureComplete`, `TestCoutIndisponible`, etc.)
  **masque ce bug** : elle construit ses rapports d'attribution synthétiques avec
  `"canal": "google_ads"` (ligne 104, 168, 200…) au lieu du `"google"` réel produit par
  `attribution_engine.py` sur les fixtures S013 — les tests passent, la jointure réelle échoue.
  **Correctif** : une table de correspondance canal→plateforme_ads explicite (ex. déjà esquissée
  par `roi-mapping.v1.yaml` au niveau fenêtre, à généraliser au niveau canal :
  `{"google": "google_ads", "facebook": "meta", "gbp": "gbp_natif"}`), + un test qui rejoue le
  pipeline **attribution réelle → roi_engine** (pas des dicts à la main) pour `google` afin
  d'empêcher la régression.

### 1.2 `nb_leads_attribues` codé en dur à 0

`Modules M/M7-marketing/src/roi/roi_engine.py:123-125` :
```python
# nb_leads_attribues n'est pas déductible sans lien campagne→lead individuel,
# nous le laissons à 0 conformément au périmètre de S015.
nb_leads = 0
```
Documenté comme limite de périmètre assumée (pas un bug caché), mais **jamais levée depuis**. La
métrique `m7_roi_cout_par_lead_fenetre` du rapport `par_fenetre` est donc structurellement
inutilisable. **Correctif** : porter l'identifiant `campagne`/`fenetre_id` jusqu'au lead au moment
de l'attribution (`attribution_engine.py` connaît déjà `camp_dern`/`fenetre` par visite — il suffit
de propager `campagne` en plus de `canal` dans `par_canal`/`par_campagne`, puis de la fenêtre via
`roi-mapping.v1.yaml`), sans dépendance externe — c'est un défaut d'architecture interne, pas un
manque de brique OSS.

### 1.3 Devise EUR/CAD incohérente dans le dictionnaire de métriques

`Modules M/M7-marketing/metrics/m7-metrics.v1.yaml` :
- ligne 10 : `unite: "CAD/lead"` (Coût par lead)
- ligne 17 : `unite: "EUR/soumission"` (Coût par soumission) — **résidu d'un gabarit non
  francisé/québécisé**, alors que le produit est 100 % QC/CAD (TPS/TVQ, Loi 25).
- lignes 87, 108 : `CAD/lead` (S013-S015) — cohérent.

Conséquence en aval : `Modules M/M8-analytics/src/m8_analytics/dictionnaire.py:41-49` valide
seulement que `unite` est une **chaîne non vide** (`CHAMPS_DEFINITION_METRIQUE`), sans jamais
vérifier son contenu — le bug **traverse silencieusement la frontière M7→M8** et atterrit tel quel
dans le dictionnaire canonique consommé par tout le reste du produit (dashboard, M9). **Correctif
double** : (a) corriger la ligne 17 en `CAD/soumission` ; (b) ajouter à `dictionnaire.py` une garde
regex sur `unite` (`^[A-Z]{3}/\w+$` avec devise ∈ `{CAD}` en v1) pour que ce type de résidu devienne
un rejet nommé (`erreurs.append(...)`) au lieu d'un silence — exactement le patron « rejet nommé,
jamais une entrée fabriquée » déjà appliqué partout ailleurs dans M8.

### 1.4 Schéma `Organization` vs `LocalBusiness` — contradiction interne, pas juste un choix à faire

C'est plus grave qu'un simple oubli : **deux gardes internes à M7 s'imposent mutuellement des
exigences contradictoires sur le même JSON-LD**.
- `Modules M/M7-marketing/src/site/generator.py:61` génère `"@type": "Organization"`.
- `Modules M/M7-marketing/src/site/guardrail.py:429` (règle **G-15**, garde-fou bloquant à la
  génération du site) : `if ld.get("@type") != "Organization": violations.append(...)` — **rejette
  explicitement toute valeur autre que la chaîne littérale `"Organization"`**, donc interdit
  `LocalBusiness`.
- `Modules M/M7-marketing/src/aeo/aeo_engine.py:284-332` (règle **A-08**, surface `perplexity`,
  contrôle de cohérence NAP nom/téléphone) : exige
  `parsed.get("@type") == "LocalBusiness"` pour même chercher un NAP — sinon verdict
  `non_conforme` / `pas_de_localbusiness_jsonld` **systématique**.

Résultat mesurable : le site produit par le pipeline actuel **échoue toujours** la règle AEO A-08
(zéro visibilité NAP pour la surface Perplexity/IA), alors même que le générateur et son propre
garde-fou sont internement cohérents entre eux. Ce n'est pas un compromis futur à trancher, c'est
une régression déjà présente. **Correctif** : schema.org permet `LocalBusiness` (et ses sous-types
comme `HomeAndConstructionBusiness`, pertinent pour une entreprise de rénovation) en **surtype
strict d'`Organization`** — tous les champs actuels (`name`, `url`, `description`) restent valides,
il suffit d'ajouter `address`/`telephone`/`geo`. Corriger (i) `generator.py` → émettre
`"HomeAndConstructionBusiness"` avec les champs NAP réels du profil brand, et (ii) `guardrail.py`
G-15 → vérifier l'appartenance à un ensemble `{"Organization", "LocalBusiness",
"HomeAndConstructionBusiness", ...}` (ou l'héritage schema.org) plutôt qu'une égalité stricte à un
seul littéral. Aucune brique externe requise — défaut de contrat interne uniquement.
