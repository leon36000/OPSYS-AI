## 0. Méthode et légende

- **Licence** : vérifiée soit par lecture directe du fichier `LICENSE`/`LICENSE.txt`/`COPYING` via `raw.githubusercontent.com` (fiable, contenu brut), soit par la doc officielle du projet (citée). Marqué **NON VÉRIFIÉ** sinon.
- **Maturité** : étoiles GitHub et signal d'activité obtenus via lecture de la page GitHub publique (WebFetch) + recoupement WebSearch. La page GitHub rendue ne restitue pas toujours l'horodatage exact du dernier commit/release ; quand seul le nombre de commits est disponible, c'est noté et le champ date exacte est marqué **NON VÉRIFIÉ (précis)** — le niveau d'activité qualitatif (actif / stable / ralenti) reste lui sourcé.
- **api.github.com** est bloqué dans cette session sandbox pour les dépôts non attachés (message : « GitHub access to this repository is not enabled for this session »). Attacher ~30 dépôts tiers via `add_repo` uniquement pour lire une licence aurait été disproportionné et hors du périmètre de l'outil (prévu pour cloner/opérer, pas pour l'audit de licence en lecture). `raw.githubusercontent.com` (non bloqué) et les pages web publiques ont donc servi de source.
- Contraintes de licence produit (rappel du brief) : MIT/Apache-2.0/BSD/MPL = OK. LGPL = OK en dépendance dynamique. **GPL/AGPL = uniquement comme service séparé non modifié derrière une frontière réseau**, jamais vendorisé/importé dans le code propriétaire OPSYS (sinon obligation de publier le code). Licences source-available/communautaires avec restrictions d'usage = signalées comme risque.

## 1. État des lieux du code existant (constat de lecture)

M1 et M2 sont livrés en **« mode ombre »** (Epic E / Epic F, vague 1) : ~100 % logique métier Python déterministe, zéro réseau, zéro horloge système, zéro appel LLM. C'est un squelette d'audit et de garde-fous déjà solide, prêt à recevoir de vraies intégrations derrière ses points d'extension :

**M1** (`src/m1_front_office/`) : `registre.py` (log append-only hash-chaîné, **en mémoire** — `self._entrees: list[dict]`), `phases_voix.py` (FSM des phases 0→5, transitions strictement linéaires), `garde_fou.py` (regex déterministes anti prix/date/engagement/aveu, **avant TTS**), `qualification.py` (extraction règles, zéro LLM), `provenance.py` (anti-injection R-015, neutralisation par jeton), `consentement.py` (gate opt-in fail-closed pour l'enregistrement), `adaptateurs.py` (`Protocol` `ApprovalEngine`/`BusNotifications`, implémentations in-memory), `digest.py`. Roadmap déjà explicite dans le PRD (§3) : SIP réel, STT/TTS locaux, Pipecat Flows/LiveKit, barge-in VAD, missed-call rescue = **GATED_T3** (hors v1, nécessite décision humaine T3).

**M2** (`src/m2_revenue_crm/`) : mêmes patrons dupliqués à dessein (décision d'architecture D3, aucun couplage M1↔M2 même en test) — `registre.py`, `statuts.py` (FSM à 4 statuts), `doublons.py` (dédup **exact-match** sur `contact_identique` OU `ville_et_travaux`, fenêtre 7 j, jamais de fusion automatique), `readiness.py` (gate M3 pure + marqueur signé recalculable), `interactions.py`, `adaptateurs.py` (`Protocol AdaptateurCRM.ecrire()`, implémentation `AdaptateurMemoire` fail-closed hors mode ombre), `frontieres.py` (détection prix/date dans les valeurs).

Conséquence directe pour R6 : **le "cerveau" (état, audit, garde-fous, gates) existe déjà et est testé (331+533 tests)**. Le travail de brique consiste à câbler l'**I/O réelle** (voix, téléphonie, CRM externe) derrière les `Protocol` déjà prévus, sans toucher à la logique métier gelée.

### 2.9 Latence ≤ 800 ms p50 — synthèse budget

Sources concordantes : Pipecat/LiveKit annoncent **750-950 ms de bout en bout** sur une combinaison STT cloud + LLM + TTS cloud typique ; un pipeline optimisé (turn-detection sémantique + TTS streaming rapide) descend à **550-700 ms p50**. Pour tenir ≤800 ms p50 sur ce projet : STT local (faster-whisper, ~100-200 ms sur un segment court) + LLM rapide + **Cartesia (40-90 ms TTFA)** est la combinaison la plus tendue en latence ; ElevenLabs (75-300 ms) reste compatible mais consomme plus de marge. À mesurer en conditions réelles VPS avant de figer le choix TTS par défaut.

**Décision structurante** : **aucun** CRM candidat n'est à la fois (a) Python-natif **et** (b) sous licence permettant le vendoring dans le code propriétaire OPSYS. Le seul favorable en licence (Odoo, LGPL) est disproportionné en poids ; le seul Python-natif (Frappe CRM) est AGPL. **Conséquence : le cœur métier M2 déjà écrit (registre hash-chaîné, FSM des statuts, dédup, readiness gate) reste l'autorité et n'est PAS remplacé.** Un CRM externe (EspoCRM en premier choix : plus léger que SuiteCRM/Odoo, plus proche "métier PME" que Twenty côté fonctions rapport/calendrier) peut être branché en **sidecar non modifié, en pure façade d'affichage** pour les représentants commerciaux qui préfèrent une UI CRM classique (kanban, calendrier), tout en gardant le registre M2 comme source de vérité auditée. Ce sidecar est **optionnel et différable** ; le modèle de données de Twenty/EspoCRM/Frappe CRM sert dès maintenant d'**inspiration gratuite** pour enrichir `LeadM2` (ex. champs Client 360, timeline d'activité).

**Choix retenu : Splink**, en complément (jamais en remplacement) du matching exact déjà en place — même philosophie fail-closed / jamais de fusion automatique que `doublons.py`.

### 3.3 Scoring de leads (ML simple)

Le brief demande un scoring "ML simple", pas un candidat unique nommé. Recommandation : **[scikit-learn](https://github.com/scikit-learn/scikit-learn)** (**BSD-3-Clause**, [LICENSE](https://raw.githubusercontent.com/scikit-learn/scikit-learn/main/COPYING), très mature, standard de facto) — une régression logistique ou un gradient boosting léger sur des features structurées déjà présentes dans `LeadM2` (canal, ville, urgence déclarée, délai de première interaction, statut d'historique) suffit largement ; interprétable (coefficients/feature importance), pas de vendor lock-in, pas de coût d'inférence cloud. **Intégration : pip, module `scoring.py` additionnel dans M2, fonction pure comme le reste du module (score = f(features) → float), jamais un LLM pour ce calcul** (cohérent avec "zéro LLM" déjà en vigueur dans M1/M2 pour les décisions déterministes). Effort **S**.

### 3.4 Relances / séquences / SLA

Aucune brique dédiée n'est nécessaire : le patron `prochaine_action` (description + échéance ISO-8601) existe déjà dans M2 et suffit à représenter une relance programmée. Pour l'exécution (déclenchement à échéance), **[APScheduler](https://github.com/agronholm/apscheduler)** (**MIT**, [LICENSE.txt](https://raw.githubusercontent.com/agronholm/apscheduler/master/LICENSE.txt)) est la brique standard Python pour cadencer les relances/SLA sans introduire de file de message externe (cohérent VPS mono-nœud). Effort **S**. Le SLA lui-même (délai max avant première action) est déjà calculable en pur Python depuis le registre (`digest.py` signale déjà les leads orphelins à 48h) — pas de brique tierce requise, seulement l'ajout d'un ordonnanceur pour déclencher les vérifications.

## 5. RECETTE — fusion dans OPSYS

1. **Docker-compose VPS mono-nœud** : un service `m1-voice-agent` (Pipecat + faster-whisper local + client SDK Twilio/ElevenLabs), un service optionnel `chatwoot` (image officielle CE), un service optionnel `espocrm` (image officielle, activé seulement si le client veut une UI CRM dédiée), le tout derrière le même réseau docker que le core Python M1/M2/PostgreSQL déjà prévu par le projet. Aucun de ces services n'est modifié à la source (respect GPL/AGPL/MPL) — toute logique métier reste dans le code propriétaire OPSYS qui les *appelle*.
2. **PostgreSQL comme backend du registre** : `Registre` (M1 et M2) est aujourd'hui une simple liste Python en mémoire. Il suffit d'écrire un second adapter respectant exactement la même interface (`ajouter`/`lire`/`tete`/`valider_chaine`) mais persistant dans une table Postgres append-only (colonnes : ligne_id, precedent_ligne_id, horodatage, payload JSONB) — **zéro changement dans phases_voix.py/statuts.py/doublons.py/readiness.py**, qui ne connaissent que l'interface.
3. **Dashboard central** : consomme l'API du core Python (M1/M2), pas directement les sidecars (Chatwoot/EspoCRM) — ces derniers restent des vues optionnelles pour les opérateurs qui les préfèrent, jamais la source de vérité. Le dashboard expose la config des modèles (cloud vs locaux) déjà exigée par le propriétaire, y compris le choix STT/TTS par canal.
4. **Économie de tokens** : la hiérarchie de coût est déjà dans le classement Tier 1→3 — le garde-fou regex, la qualification par règles, le scoring scikit-learn et la dédup Splink tournent **sans LLM**. Le seul poste LLM significatif dans M1 est la conversation elle-même (le "cerveau" conversationnel, hors périmètre de ce brief) ; NeMo Guardrails n'est activé qu'en seconde ligne sur cas ambigus pour ne pas doubler le coût sur 100 % du trafic.
5. **Adaptateurs = point de bascule mode ombre → réel** : chaque `Protocol` déjà écrit (`AdaptateurCRM.ecrire()` en M2, `ApprovalEngine`/`BusNotifications` en M1) reçoit une implémentation concrète par brique retenue (ex. `AdaptateurEspoCRM`, `BusNotificationsTwilio`) sélectionnée via la même fabrique fail-closed (`construire_adaptateur(nom_cible, mode)`) déjà en place — bascule pilotable depuis le dashboard central, sans toucher à la logique métier gelée et testée.

## 7. Réutilisation/adaptation précise du code Python existant

- **`registre.py` (M1 et M2)** : interface (`ajouter`, `lire`, `tete`, `valider_chaine`) déjà découplée du stockage (`self._entrees` = simple liste). → écrire `RegistrePostgres` implémentant la même interface ; zéro changement dans les appelants.
- **`phases_voix.py`** : la FSM des phases 0→5 est déjà 100 % transport-agnostique. → l'intégrer comme callback à chaque changement d'état du pipeline Pipecat (un `FrameProcessor` custom appelle `transitionner()` avant de faire avancer le noeud de flux vocal) ; le pipeline audio/texte réel ne fait qu'exécuter ce que la FSM autorise.
- **`garde_fou.py`** : à brancher comme dernier `FrameProcessor` **juste avant le noeud TTS** dans Pipecat — bloque toute synthèse vocale d'un texte interdit, exactement comme prévu par l'architecture M1 §4.
- **`provenance.py`** : à appeler systématiquement en tête de chaque adaptateur d'entrée (imap-tools pour courriel, webhook Chatwoot pour chat, transcription STT pour voix) avant toute construction de prompt — un seul point de filtre déjà écrit, à réutiliser N fois.
- **`consentement.py`** : la fonction `verifier_consentement` ne change pas ; seule la *source* du champ `consentement_enregistrement` devient réelle (prompt IVR + DTMF/réponse verbale captée par Pipecat au lieu d'une fixture).
- **`adaptateurs.py` (M1 et M2)** : les `Protocol` (`ApprovalEngine`/`BusNotifications` en M1, `AdaptateurCRM` en M2) sont le point d'injection direct de chaque brique retenue (Twilio pour le bus de notifications, EspoCRM/Twenty pour `AdaptateurCRM.ecrire()`) — la fabrique fail-closed existante (`construire_adaptateur`) n'a besoin que d'un nouveau mode dans son énumération `MODES`, jamais d'une réécriture.
- **`doublons.py`** : `detecter()`/`signaler()` restent l'unique chemin d'écriture d'un signalement — Splink alimente `signaler()` en tant que **second détecteur**, jamais en remplacement, préservant l'invariant "jamais de fusion automatique".
- **`digest.py` (M1 et M2)** : déjà l'endroit naturel pour afficher, demain, le score de lead (M2) ou l'état de charge du pipeline voix (M1), sans changer sa garantie de reproductibilité byte-identique (le score serait juste une donnée de plus dans le registre source).

## 9. Note Loi 25 / souveraineté des données

Tous les services cloud cités (Twilio, Telnyx, Deepgram, AssemblyAI, ElevenLabs, Cartesia, Meta WhatsApp) sont opérés par des entreprises hors Québec et impliquent une **communication de renseignements personnels à l'extérieur du Québec**, ce qui déclenche sous la Loi 25 une évaluation des facteurs relatifs à la vie privée avant la transmission, ainsi qu'une information du client ([source](https://www.cai.gouv.qc.ca/protection-renseignements-personnels/sujets-et-domaines-dinteret/principaux-changements-loi-25)). **Les briques auto-hébergées (faster-whisper local, Piper/Kokoro locaux) évitent structurellement cette exigence** pour les flux qui peuvent rester sur le VPS — un argument de poids supplémentaire, au-delà du seul coût, pour les préférer par défaut et ne router vers le cloud (ElevenLabs/AssemblyAI/Twilio) que pour les cas où la qualité voix/latence l'exige vraiment.
