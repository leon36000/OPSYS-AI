# ADR M7-S007 — Chantier terminé → contenu social (mode ombre)

> Architecte : MiMo-Pro-V2 (prose, 1re passe conforme). Adaptations d'exécution tracées : villes fictives QUÉBEC (cohérence secteur S008a) ; API réelle S005 = publier(SocialPost) — flag OFF lève AdapterDisabled, enabled+dry_run=False lève NotAutorise : le workflow configure enabled pour prouver la porte PROFONDE (acceptance), les tests prouvent les DEUX portes ; orthographe « metriques ».

**Statut** : Proposé
**Dépend de** : M7-S006 (Content Factory), M7-S005 (Postiz GATED), Brand Core v1
**Décideurs** : équipe architecture ForgeAI

---

## 1. Schéma des fixtures chantier

Chaque chantier est décrit par un fichier `fixtures/chantiers/<slug>/chantier.yaml` où `<slug>` est un identifiant lisible sans espaces (ex. `villa-nice-2024`). Le schéma impose les champs suivants : `fictif` (booléen, obligatoire, doit valoir `true` — tout chantier absent de cette mention est rejeté par le validateur avant toute composition, garantissant qu'aucune donnée réelle ne passe en mode ombre) ; `ville` (chaîne non vide, ex. `Nice`) ; `type_travaux` (chaîne non vide parmi `renovation_totale`, `extension`, `ravalement`, `isolation_thermique`) ; `date_fin` (chaîne ISO-8601, ex. `2024-03-15`) ; `description_factuelle` (chaîne non vide, 50-500 caractères, texte factuel sur les travaux réalisés) ; `photos` (liste de chaînes, chemins relatifs déclaratifs du type `photos/avant.jpg` — les fichiers binaires n'existent pas dans le dépôt, seuls les chemins sont consignés comme preuve de structure). Deux chantiers fictifs minimum sont livrés : `villa-nice-2024` (rénovation totale) et `appartement-lyon-2024` (extension), tous deux avec `fictif: true` explicite.

## 2. Orchestration du workflow

Le workflow vit dans `src/workflows/chantier_social.py`. Une fonction publique `orchestrer_chantier_vers_social(chemin_chantier: str, timestamp: str, acteur_propose: str, acteur_approuve: str) -> dict` est le point d'entrée unique. Elle exécute cinq étapes séquentiennes, chacune traçable par un statut dans le dictionnaire de résultat. Étape 1 « charge » : lecture et validation YAML du chantier via `yaml.safe_load`, rejet si `fictif` n'est pas `true`. Étape 2 « compose » : appel à `build_content_item(brand, surface="google_aio", type="post_social", sujet=description, timestamp)` qui retourne un content-item conforme au schéma v1. Étape 3 « propose » : appel à `approval.propose(item, acteur_propose, timestamp)` qui inscrit l'item dans la file avec le statut `PROPOSE`. Étape 4 « approuve » : appel à `approval.approve(item, acteur_approuve, timestamp)` — l'architecture impose que `acteur_approuve` soit différent de `acteur_propose`, conformément à l'interdiction d'auto-approbation déjà codifiée dans le module d'approbation. Étape 5 « publication » : tentative de publication via `PostizAdapter.publish(item)`. Le dictionnaire de résultat contient les clés `chantier_slug`, `etapes` (liste ordonnée de dictionnaires `{nom, statut, detail}`), et `metricues` (dictionnaire de compteurs, cf. §4). Chaque étape enregistre `statut=SUCCES` ou `statut=ECHEC` avec le détail associé (message d'exception ou objet retourné).

## 3. Preuve du gating

Lors de l'étape 5, `PostizAdapter.publish(item)` lève systématiquement `NotAutorise` car le feature-flag est OFF et l'Approval Engine absent. Le workflow capte cette exception dans un bloc `except NotAutorise` explicite, enregistre l'étape avec `statut=SUCCES` (le gating a fonctionné comme prévu) et `detail="NotAutorise capturé : écriture réelle interdite en mode ombre"`. Cette capture volontaire constitue la preuve contractuelle que la porte de sortie réseau est verrouillée. L'exception n'est jamais avalée silencieusement — elle est tracée dans le résultat — et n'est jamais re-levée, ce qui permet au workflow de se terminer proprement. Tout autre type d'exception (ex. `AdapterDisabled`) est capturé séparément avec `statut=ECHEC` et le message d'erreur associé, puis re-levé pour signaler une anomalie non prévue.

## 4. Compteurs déterministes

Trois compteurs sont ajoutés au dictionnaire de résultat sous la clé `metricues`. `chantiers_traites` (incrémenté de 1 à chaque appel réussi de `orchestrer_chantier_vers_social`, déterministe par construction) ; `contenus_proposes` (incrémenté de 1 si l'étape « propose » aboutit, 0 sinon) ; `publications_bloquees_gated` (incrémenté de 1 si et seulement si l'étape 5 capture un `NotAutorise`). Ces compteurs vivent exclusivement dans le dictionnaire retourné par l'orchestrateur — aucune écriture disque n'est requise, le consommateur M8 les agrégera à son niveau. La somme `contenus_proposes == chantiers_traites` dans le cas nominal (zéro erreur en amont) garantit le déterminisme attendu par la chaîne d'acceptance.

## 5. Anti-dérive et stratégie de tests

Six tests RED/GREEN couvrent la chaîne complète. Test 1 : refus d'une fixture sans `fictif: true` (ValueError levé, chantier jamais composé). Test 2 : composition réussie avec une fixture valide (content-item conforme au schéma v1 retourné). Test 3 : proposition et approbation par deux acteurs distincts (statuts `PROPOSE` puis `APPROVED` dans la file). Test 4 : rejet de l'auto-approbation (ValueError si acteur identique). Test 5 : capture de `NotAutorise` lors de la tentative de publication (preuve du gating, `publications_bloquees_gated == 1`). Test 6 : déterminisme des compteurs sur deux exécutions successives avec `reset()` entre chaque appel (résultats strictement identiques). Chaque test vérifie une étape isolée mais la suite complète valide l'intégration bout-en-bout. La contrainte « zéro réseau » est garantie par l'absence totale de fixtures binaires et par le fait que `PostizAdapter` en mode ombre n'émet jamais de requête sortante. Les fixtures `villa-nice-2024` et `appartement-lyon-2024` servent de données d'entrée partagées entre tous les tests, assurant la reproductibilité.
